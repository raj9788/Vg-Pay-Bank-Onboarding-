\section{High-Level Onboarding Process}

Welcome to the \textbf{VG Pay Bank Onboarding Process}. This handbook maps out every step required to integrate a Tier-2, Cooperative, or Regional Bank into the VG Pay ecosystem as a \texttt{BankPartner}.

\subsection{Onboarding Journey (Post-Agreement)}

\begin{enumerate}
    \item \textbf{Phase 1: Initiation \& Discovery (Week 1)}
    \begin{itemize}
        \item \textbf{Kick-off Meeting:} Alignment on business goals and architecture.
        \item \textbf{Information Gathering:} Bank IT completes the Information Collection Template (see Section 10).
    \end{itemize}
    \item \textbf{Phase 2: Configuration \& Tenant Setup (Week 2)}
    \begin{itemize}
        \item \textbf{Tenant Creation:} VG Pay Ops creates the \texttt{BankPartner} entity.
        \item \textbf{Role Provisioning:} VG Pay provides the \texttt{BANK\_ADMIN} credentials.
    \end{itemize}
    \item \textbf{Phase 3: Technical Integration (Week 3 - 4)}
    \begin{itemize}
        \item \textbf{Webhook Integration (Bank as PSP):} Bank develops the outbound event push to VG Pay's \texttt{/api/transactions} (or the Razorpay-compatible webhook) for payment successes.
        \item \textbf{Zero Ticketing Integration:} No development is required for the ticketing system, as it is handled natively by VG Pay.
        \item \textbf{Network Whitelisting:} Bank whitelists VG Pay API Gateways.
    \end{itemize}
    \item \textbf{Phase 4: Testing \& UAT (Week 5)}
    \begin{itemize}
        \item \textbf{UAT Environment:} Testing will be conducted in the actual live/UAT environment using 1-2 physical Soundbox devices provided to the Bank.
        \item \textbf{Functional Testing:} Simulating Agent onboarding a merchant, mapping a Soundbox, and validating Merchant Bulk Upload CSVs (if applicable).
        \item \textbf{Transaction Testing:} Simulating a live UPI transaction from the Core Banking System to VG Pay and verifying the audio alert on the physical device.
    \end{itemize}
    \item \textbf{Phase 5: Production Go-Live (Week 6)}
    \begin{itemize}
        \item \textbf{Production Deployment:} Configurations promoted to PROD.
        \item \textbf{Penny Drop:} Real INR 1 transaction on a live Soundbox.
    \end{itemize}
\end{enumerate}

VG Pay operates a multi-tenant, event-driven architecture designed to manage Merchants and their IoT Devices (Soundboxes).

\subsection{System Architecture Details}
\begin{itemize}
    \item \textbf{Direct Bank Transfers:} VG Pay does not hold, route, or settle funds. All UPI and digital transfers are processed directly between the payer's bank and the merchant's bank account. VG Pay acts strictly as a real-time notification and IoT management layer.
    \item \textbf{Success-Only Triggers:} The VG Pay system is designed exclusively to trigger the Soundbox audio. Therefore, it only expects to receive webhooks for \textbf{SUCCESSFUL} transactions. Failed or pending transactions should not be pushed to VG Pay.
\end{itemize}

\subsection{User Hierarchy (Roles \& Permissions)}
Every user in the system is assigned specific roles that govern their access:
\begin{itemize}
    \item \textbf{SUPER\_ADMIN:} Supreme access to VG Pay. Manages all banks, devices, and global configurations.
    \item \textbf{PSP\_ADMIN (Bank Admin):} Top-level administrator for a specific \texttt{BankPartner}. Manages regional operations, field agents, and can view aggregate reports for their bank.
    \item \textbf{PSP\_AGENT:} Field agent using the Agent Mobile App to onboard pre-verified merchants and map Soundboxes.
    \item \textbf{MERCHANT:} The end-user receiving payments. Currently, the Merchant App is strictly for \textbf{viewing transaction history}. Since funds settle directly into the merchant's bank account, the app is read-only regarding financial operations.
\end{itemize}

\section{Payment Soundbox (S1) - Device Overview \& Manual}

To ensure Bank IT and operational teams understand the edge-device capabilities, this section details the hardware and software specifications of the S1 Payment Soundbox.

\subsection{Hardware Anatomy \& Setup}
\begin{itemize}
    \item \textbf{Box Contents:} 1 Unit of Sound Box S1.
    \item \textbf{Front View:} Large QR code for payments (BHIM UPI). Top LEDs: Status RGB (Left), Network Green (Center), Power Red (Right).
    \item \textbf{Side View:} Micro SIM Slot (for cellular), USB Type-C slot (5V-2A charging), Power Key, Reset pinhole.
    \item \textbf{Top View:} Volume UP / DOWN buttons, Replay Button (repeats last payment announcement).
\end{itemize}

\textbf{Operating Instructions:}
\begin{enumerate}
    \item \textbf{Device Setup:} Insert a Nano SIM with an active data plan. Charge for 2.5 hours using a 5V-2A adapter via Type-C.
    \item \textbf{Power On:} Long press POWER for 3 seconds. The RGB LED flashes Roseate White once to start the boot sequence.
    \item \textbf{Changing SIM:} Turn off device $\rightarrow$ Change SIM $\rightarrow$ Turn on. (If changed while on, hit Reset).
\end{enumerate}

\subsection{Power Up Sequence \& LED Indicators}

\subsubsection{Boot Phases}
\begin{enumerate}
    \item \textbf{Phase 1 (Hardware/Network Init):} Red LED (SIM check), Middle Green blink (Network search), Purple LED (DMS Registration), Cyan (FOTA check), Orange (Installing firmware).
    \item \textbf{Phase 2 (Connectivity):} Audio announces ``Sim Inserted'' (Orange LED) and ``Network Connected'' (Cyan LED).
    \item \textbf{Phase 3 (DMS \& MQTT):} Cyan (Connecting to DMS). Once connected, LED turns \textbf{Roseate White} (Firmware OK, SIM OK, Network OK). Audio: ``Device Online''.
    \item \textbf{Phase 4 (VG Pay Integration):} Roseate White indicates hitting Registration and Config APIs. If successful, device connects to VG MQTT $\rightarrow$ \textbf{Blue LED}. Audio: ``Device is ready for Payments''.
\end{enumerate}
\textit{Note: Green LED flashes during payment announcements. Purple indicates onboarding stuck. Cyan indicates MQTT unreachable.}

\subsection{Technical Specifications}
\begin{itemize}
    \item \textbf{Hardware:} Quectel EC200U Module, 4G LTE Cat-1 (2G fallback), 2000mAh Li-ion battery (3V cutoff).
    \item \textbf{Firmware:} 30-min Heartbeat interval, OTA security \& firmware integrity.
    \item \textbf{Compliance:} BIS CRS, IEC 62133 / IS 16046 (Battery safety), IS 13252.
\end{itemize}

\subsection{Troubleshooting Guide}
\begin{itemize}
    \item \textbf{Not turning on:} Charge for 30 mins using 5V-2A. If charging LED is off, try a different socket.
    \item \textbf{Not sending data to server:} Check Green LED (Fast blink = OK). If Cyan, MQTT disconnected. Press RESET to restart network stack.
    \item \textbf{No Sound / Low Volume:} Check if battery is low (amplifier disabled). Reset device to restore default volume. Check for physical blockage over speaker mesh.
    \item \textbf{Repeated Restarts:} Charge device. Check for loose SIM. Press RESET to clear corrupt configuration.
\end{itemize}

\section{Technical Integration}

The core integration requirement is for the Bank (acting as the PSP switch) to push real-time transaction events to VG Pay.

\subsection{Environment URLs}
\begin{itemize}
    \item \textbf{Main API Gateway:} \texttt{https://api.vgpayglobal.com/}
    \item \textbf{Payment / Transaction Services:} \texttt{https://payment.vgpayglobal.com/}
    \item \textbf{Merchant Services:} \texttt{https://merchant.vgpayglobal.com/}
\end{itemize}
\textit{Note: The exact UAT and PROD URLs for each specific microservice required for your integration will be provided directly by the VG Pay team during Phase 2.}

\subsection{Payment Success Webhook (Bank \texorpdfstring{$\rightarrow$}{->} VG Pay)}

When a UPI payment successfully credits the merchant's account, the Bank must immediately call VG Pay's Payment Service to trigger the Soundbox alert. The VG Pay system exposes two distinct integration pathways depending on the bank's capabilities.

\subsubsection{Pathway 1: Direct Transaction API (\texttt{POST /api/transactions})}
This is the standard API intended for direct bank integrations.
\begin{itemize}
    \item \textbf{Endpoint:} \texttt{POST /api/transactions}
    \item \textbf{Idempotency:} Driven by \texttt{transactionId} and \texttt{utr}. If a transaction with the same ID or UTR already exists, the system returns an HTTP \texttt{409 Conflict}.
    \item \textbf{Validation:} The \texttt{amount} must be greater than zero. The system also rejects payloads if an internal \texttt{id} is present in the request body.
    \item \textbf{Authentication:} Configured via API Gateway (e.g., standard API Key or mutual TLS) depending on the environment.
    \item \textbf{Success Response:} HTTP \texttt{200 OK} with the plain text body \texttt{"ACK"}.
\end{itemize}

\textbf{Sample JSON Payload (\texttt{TransactionDTO}):}
\begin{lstlisting}
{
  "transactionId": "pay_9Xb8Y7Z6a5B4c",
  "utr": "312456789012",
  "orderId": "order_xyz123",
  "merchantId": 883,
  "deviceId": 1042,
  "amount": 500.00,
  "currency": "INR",
  "status": "SUCCESS",
  "payerVpa": "customer@upi",
  "payerName": "John Doe",
  "gatewayResponse": "{\"bank_ref\": \"12345\", \"status\": \"success\"}",
  "remarks": "Payment for order xyz123",
  "firmwareVersion": "v1.0.4"
}
\end{lstlisting}

\subsubsection{Pathway 2: Payment Gateway Compatible Webhook}
This pathway is designed for banks utilizing a Razorpay-compatible webhook structure for \texttt{payment.captured} events.
\begin{itemize}
    \item \textbf{Endpoint:} \texttt{POST /api/razorpay/webhook} (or \texttt{/api/razorpay/webhook/payment})
    \item \textbf{Authentication (HMAC SHA-256):} The webhook must include the \texttt{X-Razorpay\allowbreak-Signature} header. This is an HMAC SHA-256 hex-encoded hash of the raw payload string using a pre-shared secret provided by VG Pay.
    \item \textbf{Event Matching:} The payload must specify \texttt{"event": "payment.captured"}.
    \item \textbf{Parameter Extraction:} To route the transaction to the correct device, the Bank must pass the mapping in the \texttt{payload.payment.entity.notes} object. The system automatically searches for keys such as \texttt{merchantId} or \texttt{serialNumber}.
    \item \textbf{Success Response:} HTTP \texttt{200 OK} with the plain text body \texttt{"ACK"}.
\end{itemize}

\begin{tcolorbox}[colback=blue!5!white,colframe=blue!75!black,title=How does the Bank get the Device or Merchant ID?]
For Pathway 2, the Bank embeds the VG Pay \texttt{serialNumber} or \texttt{merchantId} directly into the static/dynamic UPI QR code parameters generated for the merchant. When a customer scans and pays, these flow through the network to the Bank's switch, which extracts them and forwards them in the \texttt{notes} object of the webhook.
\end{tcolorbox}

\subsection{Merchant Management (REST API)}

Agents typically create merchants via the Mobile App, hitting the \texttt{POST /api/merchants} endpoint. Additionally, Bank IT teams can utilize the full suite of CRUD endpoints (\texttt{GET}, \texttt{PUT}, \texttt{DELETE}) to sync merchant data programmatically.

\begin{tcolorbox}[colback=red!5!white,colframe=red!75!black,title=Strict Business Rules]
\begin{itemize}
    \item \textbf{Auto-Generated Code:} The Merchant \texttt{code} (e.g., \texttt{VGPAYMERCHANT00000001}) is auto-generated by the backend. Do not pass \texttt{id} or \texttt{code} in the \texttt{POST} payload, or the request will be rejected.
    \item \textbf{Deletion \& Inactivation:} A merchant cannot be marked as \texttt{INACTIVE} or deleted if they still have devices assigned to them. You must first unassign all devices via the Device Mapping API, otherwise the system will return a \texttt{409 Conflict}.
\end{itemize}
\end{tcolorbox}

For high-volume onboarding, Bank operations can utilize the \texttt{POST /api/\allowbreak merchants/\allowbreak bulk-upload} endpoint. This accepts a CSV \texttt{multipart/\allowbreak form-data} file containing merchant details, allowing thousands of merchants to be provisioned in a single request.

\textbf{Authentication:} Bearer Token with \texttt{MERCHANT\_CREATE} / \allowbreak \texttt{MERCHANT\_VIEW} / \allowbreak \texttt{MERCHANT\_UPDATE} / \allowbreak \texttt{MRCHANT\_BULK\_UPLOAD} authorities.

\textbf{Sample JSON Payload (\texttt{MerchantDTO}):}
\begin{lstlisting}
{
  "businessName": "Sharma Supermarket",
  "contactName": "Rahul Sharma",
  "phoneNumber": "9876543210",
  "email": "rahul@sharma.com",
  "address": "123 Main St, Hinjawadi, Pune",
  "bankPartnerId": 1
}
\end{lstlisting}

\subsection{Device Mapping (REST API)}

To map a physical Soundbox to a Merchant, the Agent App calls the \texttt{POST /api/\allowbreak merchant-devices} endpoint. This maps the device and merchant IDs and marks the physical device as \texttt{ASSIGNED} in the system.

\textbf{Business Rule:} Devices can only be assigned to a merchant if the merchant's status is \texttt{ACTIVE}. If the device is already assigned elsewhere, the API returns a \texttt{409 Conflict}.

\textbf{Authentication:} Bearer Token with \texttt{MERCHANT\_DEVICE\_MANAGE} authority.

\textbf{Sample JSON Payload (\texttt{MerchantDeviceDTO}):}
\begin{lstlisting}
{
  "merchantId": 9845,
  "deviceId": 2049,
  "bankPartnerId": 1
}
\end{lstlisting}

\subsection{Standard HTTP Responses}
\textbf{Standard Response Payload (\texttt{ResponseDTO}):}
All REST endpoints (except raw webhooks returning "ACK") follow a standardized JSON envelope:
\begin{lstlisting}
{
  "responseCode": 200,
  "responseMessage": "Success Message",
  "data": { ... } // Or null in case of error
}
\end{lstlisting}

The VG Pay APIs utilize standard HTTP status codes. Expected responses include:
\begin{itemize}
    \item \textbf{200 OK:} Success / Acknowledged. Returns \texttt{"ACK"} for transaction webhooks.
    \item \textbf{400 Bad Request:} Invalid input or missing fields (e.g., missing or zero \texttt{amount}, passing an internal \texttt{id} on a POST request).
    \item \textbf{401/403 Forbidden:} Invalid HMAC signature (\texttt{X-Razorpay-Signature}) or unauthorized access.
    \item \textbf{404 Not Found:} Requested resource (e.g., Device or Transaction) not found.
    \item \textbf{409 Conflict:} Duplicate resource detected (e.g., a transaction with the same \texttt{transaction\allowbreak Id} or \texttt{utr} already exists).
    \item \textbf{500 Internal Server Error:} Unexpected server-side failure or parsing error.
\end{itemize}

\section{Security \& Infrastructure Checklist}

\begin{tcolorbox}[colback=red!5!white,colframe=red!75!black,title=IMPORTANT]
Security is paramount. The following must be adhered to before UAT sign-off.
\end{tcolorbox}

\begin{itemize}
    \item \textbf{Data Residency \& Cloud Infrastructure:} The VG Pay backend is currently hosted on \textbf{AWS Mumbai}, ensuring all merchant and transaction data is stored strictly within India to comply with data localization regulations. Additionally, the microservices architecture allows the VG Pay backend to be deployed \textbf{On-Premise directly on the Bank's own servers} if strict internal policies require it.
    \item \textbf{Mobile App Security (Zero-Trust):} The VG Pay Agent and Merchant mobile applications natively enforce \textbf{Root \& Jailbreak Detection} blocking execution on compromised devices. Access is further gated by mandatory \textbf{Biometric Authentication} (Fingerprint/FaceID).
    \item \textbf{SSL/TLS:} All VG Pay endpoints enforce HTTPS (TLS 1.2+). HTTP traffic is instantly dropped.
    \item \textbf{Payload Encryption:} Ensure personally identifiable information (PII) like \texttt{payerVpa} is masked or handled per compliance guidelines. Internally, the VG Pay backend encrypts sensitive data (like VPA and Payer Name) before storing it in the database.
    \item \textbf{Webhook Authentication:} For Pathway 2 (Razorpay-compatible), Bank Webhooks to VG Pay must be authenticated using \textbf{HMAC SHA-256 signatures}. The bank computes a hash of the payload using a pre-shared secret and passes it in the header (e.g., \texttt{X-Razorpay\allowbreak-Signature}). The VG Pay backend actively validates this signature before processing the event. (Pathway 1 uses standard API keys / mTLS).
    \item \textbf{Network Whitelisting:} The Bank must whitelist VG Pay's Egress IPs to receive callbacks (if applicable) and VG Pay will whitelist the Bank's IPs for inbound API calls.
\end{itemize}

\section{Merchant \& Agent Onboarding Workflows}

The onboarding process encompasses creating administrative roles and field agents, leading up to merchant registration via the \textbf{VG Pay Agent App}.

\subsection{Agent Provisioning Workflow}
\begin{enumerate}
    \item \textbf{Super Admin Creation:} The VG Pay Super Admin creates a Bank Admin user within the Agent App.
    \item \textbf{Bank Admin Delegation:} The newly created Bank Admin can then onboard other bank personnel, 3rd party vendors, or direct field agents.
    \item \textbf{Merchant Onboarding Power:} Both the Bank Admins and the field Agents have the authority to onboard merchants directly.
\end{enumerate}

\subsection{Merchant Onboarding Steps}
\begin{enumerate}
    \item \textbf{Merchant Registration (e-KYC):} The Merchant is assumed to already have a KYC-verified bank account. The Agent visits the shop, enters basic details (Business Name, Phone, Address) into the Agent App, and securely captures the merchant's \textbf{Digital Signature} on-screen to legally authorize the onboarding onto VG Pay.
    \item \textbf{Approval:} The VG Pay backend registers the merchant. The Merchant's status is set to \texttt{APPROVED}.
    \item \textbf{Device Mapping:}
    \begin{itemize}
        \item Agent scans the QR code on the physical Soundbox.
        \item The app calls \texttt{POST /api/\allowbreak merchant-devices} passing the \texttt{merchantId} and the \texttt{deviceId}.
        \item The backend validates the mapping and creates a record in the \texttt{MerchantDevice} table, marking the device as \texttt{ASSIGNED}.
        \item \textit{Note:} During this first assignment, the backend automatically provisions a \texttt{PSP\_\allowbreak MERCHANT} user login for the merchant to access the Merchant App.
    \end{itemize}
    \item \textbf{Activation:} The Soundbox connects to the MQTT broker, downloads initial config, and is ready for the first transaction.
\end{enumerate}

\section{Ticketing \& Support Flow}

VG Pay natively integrates with the \textbf{VG Ticketing System} to provide a seamless, closed-loop support flow for both merchants and field agents.

\begin{tcolorbox}[colback=green!5!white,colframe=green!75!black,title=No Bank Integration Required]
The Bank IT team is \textbf{not} required to integrate their own ticketing system or develop any webhooks for this process. The entire support lifecycle, including ticket creation and resolution notifications, is handled completely internally within the VG Pay ecosystem.
\end{tcolorbox}

\subsection{End-to-End Ticketing Architecture}
\begin{enumerate}
    \item \textbf{Ticket Creation (Mobile App $\rightarrow$ VG Pay):}
    \begin{itemize}
        \item Merchants or Agents can raise complaints (e.g., Soundbox hardware faults, transaction disputes) directly from their mobile application.
        \item The mobile app sends a \texttt{POST /api/complaints} request to the VG Pay backend, passing a \texttt{ComplaintsDTO} payload with the issue details and the merchant ID.
    \end{itemize}

    \item \textbf{System Forwarding (VG Pay $\rightarrow$ VG Ticketing System):}
    \begin{itemize}
        \item Upon receiving the complaint, the VG Pay backend validates the payload, generates a unique internal \texttt{referenceNumber}, and triggers an asynchronous notification (\texttt{notify-merchant-complaint}).
        \item The issue is securely forwarded to the VG Ticketing System via an outbound API call, converting it into an actionable support ticket for the operations team.
    \end{itemize}

    \item \textbf{Ticket Tracking (Mobile App $\rightarrow$ VG Pay):}
    \begin{itemize}
        \item Merchants can track their open ticket statuses by calling the \texttt{GET /api/\allowbreak complaints/\allowbreak all} endpoint. This supports pagination, filtering, and sorting.
    \end{itemize}

    \item \textbf{Resolution \& Webhook (VG Ticketing System $\rightarrow$ VG Pay):}
    \begin{itemize}
        \item When the support agent marks the ticket as "Closed" or "Resolved" in the VG Ticketing System, it fires a webhook back to VG Pay's \texttt{TicketWebhookController}.
        \item Specifically, the system sends a \texttt{TicketClosed\allowbreak WebhookDTO} payload to the \texttt{POST /api/\allowbreak ticketing/\allowbreak ticket-closed} endpoint.
    \end{itemize}

    \item \textbf{Final Notification (VG Pay $\rightarrow$ Merchant):}
    \begin{itemize}
        \item The VG Pay backend processes this closure event and immediately triggers a push notification to the merchant's device (via Firebase Cloud Messaging) to inform them that their issue is resolved.
    \end{itemize}
\end{enumerate}

\subsubsection{Support Levels and Escalation Matrix}
If an issue is at risk of breaching its SLA, or if it involves complex defects, it will be escalated through the following tiers:

\begin{itemize}

    \item \textbf{L2 (Technical Support):} Advanced diagnostics and RMA approvals. Escalates to L3 for product defects.
    \item \textbf{L3 (Engineering / OEM):} Firmware patches and product fixes. Escalates to Management for repeated failures.
    \item \textbf{Management:} Handles critical escalations and Bank-level communication for P1/Major incidents.
\end{itemize}

\section{Pre-Go-Live Checklists}

\subsection{Bank IT / Network Team}
\begin{itemize}[label=$\square$]
    \item IP Whitelisting completed for UAT and PROD.
    \item Bank switch updated to push \texttt{/api/transactions} to VG Pay on successful UPI credits.
    \item Webhook timeouts configured appropriately (recommend 3-5 seconds).
    \item Error handling built for 4xx and 5xx responses from VG Pay (refer to the Standard HTTP Responses section).
